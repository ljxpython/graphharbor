# Implement Feature

当对应 `docs/projects/` 项目存在、用户已要求实施时使用；局部改动不需要新建项目或实施记录。分级及产品边界见根目录 `AGENTS.md`。

## 开始任务

1. 读取项目 README 与 `tasks.md`，或编号专题文档；确认目标、四字段任务、验证要求及尚未解决的风险。任务没有可判定的预期结果或验证项时先补齐，再写代码。
2. 查看工作区改动，追踪实现和所有受影响调用方。修改公开协议时查客户端和错误路径；修改数据/鉴权时查恢复和拒绝路径。已有用户改动必须保留。
3. 只实现已规划的范围；发现设计与事实冲突时更新项目方案和任务，说明原因及影响，不能默默扩大范围。行为变化至少增加或更新一个能在回归时失败的相关检查。

## 每项任务的阶段验证

完成代码后运行该任务的最小相关检查，不在每个任务后跑完整 E2E。记录实际命令或手工步骤、结果、日期及未覆盖项；失败先修复并重跑受影响检查。任务完成行至少保留：改动内容、代码位置、预期结果、验证结果与状态。例如：

```markdown
- [x] Task N：CLI 默认值兼容；位置：`libs/langhost/src/langhost/cli.py`；
  预期：未传参保持原值；验证：`uv run pytest -q libs/langhost/tests/test_cli.py`，通过；
  2026-09-25 完成。
```

示例只说明记录格式，不能复制其“通过”作为实际证据。代码完成但检查未运行或失败时保留 `[ ]`，写明原因和下一步；不能以提交记录或 `implementation/` 文件代替任务进度。多专题项目在对应专题维护同等信息。

## 细节与交接

只有迁移步骤、关键设计取舍或复杂故障无法从方案、任务与代码看清时，才在 `implementation/` 写简短说明，重点写为什么和兼容影响，不复制整段 diff 或易过期行号。任务完成后将跨任务契约、恢复与安全验证交给 `verify-change` 做最终检查。沿用已有项目结构，不批量重排历史文档；不得自动提交、推送或发布。
