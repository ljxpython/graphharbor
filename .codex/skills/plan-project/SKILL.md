# Plan Project（项目规划与任务拆解）

用于在系统进行链路改动或治理改动前，制定严密的技术方案、定义边界、拆解具备可判定性结果的任务清单。**这是 AI 在接到跨包改动或治理需求后自动调用的 Skill**。

## 触发条件

- **链路改动**：涉及跨双包（`langhost` 与 `langgraph-runtime-pg`）调用、公开 Core REST/SSE 契约变更、事件时序调整或数据表 Schema 迁移
- **治理改动**：架构重构、安全性/鉴权升级、生产运维与包版本发布流程
- 需要多人或跨会话持续推进的重要工作

## 跳过条件

- **局部小改动**：单包内部无契约破坏的 bugfix、加日志、局部重构，直接实现并提交，不建项目文档
- **纯讨论与可行性咨询**：直接对话分析并给出结论；当讨论收敛且用户明确要求落地时，才触发本 Skill

---

## 工作流 (SOP)

### 1. 确定项目基础信息
- **项目目录命名**：`docs/projects/{YYYYMMDD}-{kebab-case-name}/`（若已有同目标项目，沿用旧目录，不得按新日期重复建同义目录）
- **影响包范围**：明确涉及 `libs/langhost`（网关）、`libs/langgraph-runtime-pg`（持久化）还是双包协同
- **改动级别**：判定为「链路改动」还是「治理改动」（治理改动方案必须经由人类显式评审批准方可实施）

### 2. 选择模板档位
- **默认：标准模板** — 绝大多数链路改动与中小型治理改动首选。
- **升级：多专题模板** — 仅当方案自然拆分成 **3 个以上可完全独立实施与验收的子专题**，或大型长期治理项目时采用。

### 3. 标准模板 → 多专题模板原子升级规范
升级操作必须一次性原子完成，严禁出现新旧文档并存的混乱局面：
1. **旧文档标注废弃**：在原 `plan.md`、`tasks.md`、`verification.md` 顶部分别注明：
   `> ⚠️ 本文档已拆分为多专题模板，阅读入口详见 [README.md](README.md)，本文档停止维护。`
2. **内容迁移拆解**：将原文档内容拆入对应的编号子专题文档（如 `01-xxx.md`），每篇自带目标、方案、任务清单、验证与状态。
3. **更新 README.md**：将模板类型标为 `多专题模板`，并提供 `## 阅读顺序` 导航列表，作为读者的**唯一入口纲领**。

## 标准模板结构与规范

```text
docs/projects/{YYYYMMDD}-{项目名}/
├── README.md           # 项目概览、影响范围、状态看板与决策索引
├── plan.md             # 深度架构方案、技术选型、双包边界与回滚预案
├── tasks.md            # 严格四段式任务清单（进度唯一事实源）
└── verification.md     # 验证场景设计、执行环境与最终验收报告
```

### tasks.md 必须遵循的四段式规范

任务清单中的每个 Task 必须能够独立回答以下四个核心问题，严禁使用含糊的一句话占位：

```markdown
### Task 1.1: {明确的任务名称}
- **改动内容：** {具体做什么改动，不写空话}
- **代码位置：** `{准确的文件路径}` → `{类名.函数名()}`
- **预期结果：** {改动后可判定的具体行为或输出}
- **验证项：** `{真实可运行的验证命令或具体用例}`
- **状态：** `[ ]` 待开始
```

> **示例：**
> ```markdown
> ### Task 1.1: 放通子图 checkpoint_ns 路由参数
> - **改动内容：** 在 POST /state/checkpoint 请求体中解析 checkpoint_ns 并向存储层透传
> - **代码位置：** `libs/langhost/src/langhost/protocol_api.py` → `checkpoint()`
> - **预期结果：** 传入子命名空间时正确查得子智能体快照，未传时保持默认空命名空间向后兼容
> - **验证项：** 运行针对性单测 `uv run pytest -q libs/langhost/tests/test_subagent_history.py`
> - **状态：** `[ ]` 待开始
> ```

## 规划自检清单 (Checklist)

在向用户汇报方案前，AI 必须自查以下关键点：
1. **边界检查**：是否越过了通用 Agent Server 边界？严禁在方案中向核心运行时引入业务模型供应商、特定业务工具或业务 trace。
2. **双包锁步**：方案若涉及版本调整或依赖变动，是否保证 `graphharbor` 与 `graphharbor-runtime` 双包同步对齐？
3. **测试安全**：验证设计中若包含端到端检查，是否强调了在独立隔离测试库中执行，避免误清数据？
4. **状态标定**：初始 `README.md` 与 `tasks.md` 状态必须如实标为 `规划中`，不得将未开始的任务提前打勾。
