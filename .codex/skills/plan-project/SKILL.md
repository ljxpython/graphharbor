# Plan Project

触发分级以仓库根目录 `AGENTS.md` 为准。纯讨论直接回答，除非用户明确点名本 Skill；只要求规划时，交付方案后停止，不把计划当成实施授权。

## 先核实边界

1. 搜索 `docs/projects/` 是否已有同目标项目。有则沿用它的任务和验证位置，不按日期再建一个同义目录。没有才按首次规划日期创建 `docs/projects/{YYYYMMDD}-{kebab-case-name}/`。
2. 读实际实现、调用方、相关测试和当前兼容声明；明确哪些行为已实现、哪些仍只是目标。公开契约改动要覆盖 CLI/REST/SDK/SSE 消费面中受影响的部分；数据或安全改动要找出信任边界、持久数据和失败路径。
3. 写清目标、非目标、兼容与回滚约束、风险及依赖。未知的负责人、工期或测试结果不要编占位值；阻断实施的未知项标为待决。

## 文档产物

默认使用标准模板，四份文档各有唯一职责：

| 文件 | 必须包含 |
| --- | --- |
| `README.md` | 一句话目标、影响范围、当前状态、导航、关键决策与未决事项 |
| `plan.md` | 当前事实与问题、拟变行为、契约/兼容影响、风险及回滚方式 |
| `tasks.md` | 可独立验收的任务、准确代码位置、预期结果与验证项 |
| `verification.md` | 场景、预期结果、执行条件、尚未执行项；后续记录真实证据 |

每个任务至少回答四个问题，不必套用庞大卡片：

```markdown
- [ ] Task N：改动内容；位置：`libs/langhost/src/langhost/cli.py`；
  预期结果：CLI 参数按约定生效且默认值兼容；
  验证项：补充默认值与无效参数断言后运行 `uv run pytest -q libs/langhost/tests/test_cli.py`。
```

文件和验证命令必须针对真实代码调整。协议变更写清请求/响应或事件差异与旧客户端行为；持久化变更写清迁移前后数据、失败恢复和隔离测试环境；鉴权变更写清拒绝路径和跨租户检查。没有稳定自动化时写可重复的手工步骤及判定条件，不伪装成已执行。

## 选模板与交付检查

只有至少三个可独立实施和验收的专题时，使用 README 加编号专题文档；每篇自带目标、方案、任务、验证和状态。升级已有标准模板时同步迁移内容，README 指向唯一有效位置，旧清单明确废弃，避免双份进度。

规划完成前逐项检查：任务是否覆盖方案的每个目标，验证是否覆盖任务的结果和高风险失败路径，README 的状态是否仍为规划中。`implementation/` 等实施时确有额外设计细节再建。向用户报告方案位置、关键取舍、阻断项及下一步；不要把待验证写成通过。
