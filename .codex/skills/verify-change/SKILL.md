# Verify Change

链路或治理项目需要最终验收时使用；局部改动直接运行相关检查，无需项目验证文档。标准项目读 `verification.md`，多专题项目读各专题验证小节。风险范围以根目录 `AGENTS.md` 和项目方案为准。

## 两阶段验证

| 阶段 | 时机与目的 | 记录位置 |
| --- | --- | --- |
| 阶段验证 | 每项任务完成时，运行直接相关的最小检查，防止局部实现未验证 | 任务行或专题任务小节；`implement-feature` 负责更新 |
| 最终验证 | 任务全部完成后，检查跨任务交互、对外契约、恢复和适用质量门禁 | `verification.md` 或专题验证小节；本 Skill 负责更新 |

最终验证先把项目目标、任务、阶段证据和剩余风险列出来，再选检查；不能拿“测试总数很多”替代关键场景。

| 改动面 | 应有的直接证据 |
| --- | --- |
| 文档、AGENTS、Skill | 引用路径与 frontmatter 有效，触发情境和状态规则无冲突 |
| 内部代码 | 相关回归测试，以及适用的 Ruff / 类型检查 |
| 公开 CLI、REST、SDK、SSE | 变更前后兼容预期、错误输入及受影响消费方的契约检查；事件还要核对顺序、终态和重放 |
| 持久化、迁移、worker 恢复 | 隔离且可丢弃的测试库中的迁移/回滚、重启恢复、旧数据保持和失败路径；禁止对默认或生产库运行清表测试 |
| 鉴权、租户隔离、安全 | 未授权、跨租户和拒绝路径的测试或可复现调用证据 |
| 性能或生产调度 | 只在相关时记录基线、目标、环境和结果；本地数据不能当生产结论 |
| 打包或发布准备 | 双包版本锁步、锁文件、构建和安装验证；按 `docs/standards/release-process.md` 的适用门禁执行 |

先用确定性 fixture；真实模型仅在相关端到端烟测中按 `AGENTS.md` 注入凭据，结果只留脱敏指标。完整 `scripts/test.sh` 有数据库副作用，只在确认隔离测试环境后运行。与本次改动无关的类别标“不适用”，不用凑全套测试。

## 记录证据与收尾

1. 对每项适用检查记录日期、环境、实际命令或可重复步骤、预期、结果。失败修复后重跑；跳过和未运行分别标记原因。不得根据设计文档或旧日志声称本次通过。
2. 比对 README 状态、任务勾选和最终验证结论。若任务未完成、必要证据缺失或兼容声明超前于结果，先修正文档与结论，不能标完成。
3. 用以下四态给项目结论，写清剩余风险和下一步：

| 状态 | 判定 |
| --- | --- |
| `done` | 目标范围内任务、必要阶段及最终证据齐全，状态和对外描述一致 |
| `partial` | 已有部分实现或证据，仍缺任务或必要检查；列明缺口 |
| `blocked` | 外部环境、权限或依赖阻断必要验证；写明解除条件 |
| `deferred` | 明确决定整项范围后置；写明决定与后续项目或阶段 |

单项检查使用通过、失败、跳过、未运行；这些不是项目四态。项目结论不能由 `implementation/` 文件数推断。只更新本项目受影响的进度和验证文档，不编造证据，也不把“未测试”写成“无风险”。
