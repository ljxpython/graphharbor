# Verify Change（验证改动与收尾验收）

用于在链路改动或治理改动实施完成后，执行系统化最终验证，核对证据链完整性并判定项目完成状态。**这是 AI 在所有任务开发完成后自动调用的 Skill**。

## 触发条件

- 链路改动或治理改动中所有 Task 代码编写完成
- 需要执行跨包、全量回归或端到端集成验证
- 项目收尾前需进行最终状态判定与交付核查

## 跳过条件

- 局部小改动（单包内修复/重构），直接在开发中执行针对性单元测试，不必生成项目级验证文档

---

## 两阶段验证铁律 (Two-Phase Verification)

| 阶段 | 执行时机与目标 | 责任人 / 技能 | 记录位置 | 典型命令 |
|---|---|---|---|---|
| **Phase 验证**<br/>(阶段性) | 每完成一个 Task，运行该 Task 直接相关的**最小测试**，快速闭环 | `implement-feature` | `tasks.md` 内对应的 Task 完成卡行 | `uv run pytest -q libs/langhost/tests/test_specific.py` |
| **Final 验证**<br/>(最终全量) | 方案内所有 Task 完成后，执行跨包交互、对外契约、恢复机制与回归门禁 | `verify-change` | `verification.md` 的最终验证章节 | 全量单测、端到端集成、版本锁步门禁 |

> ⚠️ **高压线警告：**
> - **严禁混淆：** 不得把 Phase 验证记录写进 Final 验证区块，两者责任分明、相互独立！
> - **严禁编造：** 验证结果必须是真实执行产物（命令输出、日志摘录或脱敏指标），未运行的测试必须诚实标注“未运行”。

---

## 验证层级与证据标准

### 1. 内部代码与双包单元测试
- **执行：** 运行各包单元测试与代码规范检查
  ```bash
  uv run ruff check .
  uv run pytest -q libs/langgraph-runtime-pg/tests
  uv run pytest -q libs/langhost/tests
  ```
- **记录：** 通过用例数、耗时、覆盖的核心模块。

### 2. 公开契约与端到端集成 (CLI / REST / SSE)
- **执行：** 验证 Core Agent Protocol、`/state/checkpoint`、心跳帧、`Last-Event-ID` 断线续传与错误状态码。
- **记录：** 请求响应脱敏片段、SSE 事件时序证据、状态机迁移是否符合预期。

### 3. 持久化、租约与容错自愈 (PG / Redis)
- **执行：** 在**独立隔离测试库**中验证迁移脚本升降级、Lease 租约超时 Reaper 回收、崩溃重启恢复。
- **安全红线：** `scripts/test.sh` 包含清库操作，**严禁对包含开发数据或未隔离的数据库运行**！

### 4. 发布与版本锁步门禁 (仅限打包发布项目)
- **执行：** 检查双包版本号一致性与锁文件：
  ```bash
  python3 scripts/check_versions.py
  ```

## 收尾核对：四处状态一致性检查

在宣布项目交付或写下最终结论前，**AI 必须严格对照以下四处，确保状态 100% 对齐**：

```text
┌────────────────────────────────────────────────────────┐
│ 1. docs/projects/.../README.md 的「状态」字段           │
│    ==                                                  │
│ 2. tasks.md 中 Task 勾选与完成卡完整度                  │
│    ==                                                  │
│ 3. verification.md 中 Phase 记录条数 == 已完成 Task 数 │
│    ==                                                  │
│ 4. docs/CONTEXT.md 中该活跃项目的状态行                 │
└────────────────────────────────────────────────────────┘
```
四处有任何一处矛盾（例如 tasks.md 没打勾但 README 写 done），必须原地修正对齐，严禁蒙混过关！

---

## 最终判定：完成度四态标准

在 `verification.md` 的「最终结论」章节，必须明确给出以下四态之一：

| 判定状态 | 严格标准 | 下一步动作 |
|---|---|---|
| **`done`** | 规划范围内所有任务 100% 完成，Phase 与 Final 证据确凿，相关文档与合规项全绿 | 触发项目收尾反思（提议经验沉淀与标准毕业），准备交付 |
| **`partial`** | 核心主干完成但存在边缘任务未实现，或缺少非阻断性验证证据 | 详细列明剩余缺口与待办项，严禁冒充 done 汇报 |
| **`blocked`** | 遇到缺少测试环境、缺少凭据或等待外部依赖阻断，导致关键验证无法执行 | 说明阻断原因、尝试过的排查手段及需要人类提供的支持 |
| **`deferred`** | 经沟通明确决定将某部分功能整体推迟至后续专项 | 记录推迟决定、理由及后续承接项目 |
