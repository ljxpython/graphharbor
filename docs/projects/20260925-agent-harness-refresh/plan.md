# GraphHarbor Agent 协作规则更新方案

## 现状与问题

本仓库 `AGENTS.md` 只有产品边界和真实模型验收规则，没有说明哪些改动需要项目文档、怎样处理已有项目、如何验证和记录状态。三份 Skill 共 835 行，仍包含平台仓库的 `apps/xxx`、`platform-web -> platform-api -> runtime-service`、不存在的多专题参考路径，以及固定 E2E、性能和逐任务实施记录模板。它们与本仓库 `libs/langhost`、`libs/langgraph-runtime-pg` 和现有项目文档的实际用法不一致。

平台仓库的 Harness 经验有价值：常驻约束与按需流程分层、任务写预期结果与验证项、验证证据对应完成状态、经验按需读取。它的三服务分级、全仓功能索引、会话快照、逐任务完成卡和全量回归要求不能原样迁移。

## 目标与边界

- 新会话可从 `AGENTS.md` 找到真实入口和不可违反的产品 / 凭据约束。
- AI 能稳定判断直接实现、规划、沿用已有项目或只回答问题；三份 Skill 的输入、产物和状态定义相互一致。
- 项目文档反映真实执行证据，不强迫对文档改动运行服务 E2E，也不把计划写成已完成。
- 规划、实施和验证只依赖 `AGENTS.md`、三份 Skill 及其生成的项目文档。
- 本项目不改运行时、协议、发布流程、个人 Skill 或平台仓库文件。

## 设计

### 1. 常驻规则：`AGENTS.md`

保留现有产品边界、存量字段说明、真实模型凭据和发布限制。补充一张简短的决策表：

| 类型 | 判断依据 | 动作 |
| --- | --- | --- |
| 讨论 / 探索 | 仅问结论，未要求落地 | 直接回答；显式点名 Skill 则按请求执行 |
| 局部改动 | 不改变外部契约、数据语义或生产安全边界 | 直接实现，做相关最小验证 |
| 链路改动 | 跨 CLI / API / worker / SDK / 事件等消费边界，或改变公开契约 | `plan-project` -> 实施 -> `verify-change` |
| 治理改动 | 架构、安全、持久化迁移、生产运维或协作规则改变 | `plan-project`；方案评审按任务/现行规则执行；实施后验证 |

分级只决定工作量和证据强度，不能把“改了多个文件”误判为链路改动。已存在对应项目文档时更新它，避免每天新建同义项目。用户只要求方案时止于规划，不隐式改代码；用户要求实现时按已授权范围继续，评审是否为硬门槛以明确用户指令和适用规则为准，不另造审批流。禁止自动 commit、push、发布或调用生产 API；这些由用户指令和现行安全约束控制。

`AGENTS.md` 指向本仓库实际的代码、测试、`CONTRIBUTING.md` 和相关 `docs/projects/`。当前能力以代码、测试和已验证的项目文档核对，不建立需每次改动同步的镜像索引。

### 2. 规划：`.codex/skills/plan-project/SKILL.md`

缩成触发入口、现有项目查重、标准 / 多专题选型和最小产物约定。默认标准模板 `README.md`、`plan.md`、`tasks.md`、`verification.md`；仅自然存在多个可独立验收专题时采用编号文档。目录名取首次规划日期。文档只写已经确认的事实和决策，工作量、负责人未知就省略，不填占位符。

`.gitignore` 只放行 `.codex/skills/`，使三个 Skill 能进入仓库版本；本机 `.codex/config.toml` 继续忽略。

任务至少写改动位置、预期结果和可执行验证项。规划阶段的 `verification.md` 写验收条件及待执行状态，不伪造通过记录。对协议、认证、状态机、迁移和发布门禁的变更，直接在项目方案中写清行为契约、兼容策略和验收条件。多专题升级时 README 指向唯一有效任务与验证位置，旧文件明确迁移或废弃。

### 3. 实施：`.codex/skills/implement-feature/SKILL.md`

从项目任务读取范围，先查现有实现和测试，再作局部改动。每完成可独立验收任务，在 `tasks.md` 或专题文档更新状态、结果与最小验证证据；未验证不得标完成。`implementation/` 只在重要设计取舍、迁移步骤或复杂故障需要额外解释时创建，不强制每个任务复制 Git diff、代码块、行号。已有项目的记录保持原有结构，不批量重排。

### 4. 验证：`.codex/skills/verify-change/SKILL.md`

按改动实际影响选择验证：文档 / Skill 改动做链接、路径、触发场景和规则一致性检查；局部代码做相关测试与 lint；协议做契约 / SDK / SSE 链路测试；持久化做隔离数据库上的迁移、重启和恢复验证；生产治理按风险补安全、性能或回滚检查。真实模型只作端到端烟测，先跑确定性 fixture。

记录命令或手工场景、日期、结果、未执行项和原因。项目级四态统一为 `done`（必要任务及证据齐）、`partial`（仍缺任务或证据）、`blocked`（外部条件阻断）、`deferred`（明确决定后置并写去向）；单项测试继续用通过 / 失败 / 未运行。README、任务和验证结论必须一致；不能以 `implementation/` 文件数量推断进度，也不能把跳过写成通过。

### 5. 质量与反馈闭环

任务写改动内容、位置、预期结果和验证项；实现后先做逐任务阶段检查，跨任务契约与失败路径再做最终验证。GraphHarbor 的公开协议、SSE、持久化、鉴权与打包各有对应证据，不以无关测试数量代替关键场景。`scripts/test.sh` 会清空测试库中的 PG 表，必须在隔离可丢弃环境执行。反复出现的通用失误回写 `AGENTS.md`，流程细节回写对应 Skill，单个项目结论留在项目文档。

## 风险与取舍

- **误把规划当实施：** 用户只要求方案时，`plan-project` 交付方案后停止；实施按已授权范围进行。
- **规则与历史项目不一致：** 仅约束后续工作，不要求追改历史文档；引用旧项目时以其实际结构为准。
- **平台模板重新膨胀：** 不迁移 `CONTEXT.md`、`FEATURES.md` 或经验库；出现反复定位成本再以真实案例评估增设。

## 实施顺序

1. 先更新 `AGENTS.md` 的决策入口和现有文档指针。
2. 再精简三个 Skill，使触发、产物和状态语义一致。
3. 用 `verification.md` 的代表性场景走查，并核对 Markdown 链接、旧平台路径和关键安全约束。
